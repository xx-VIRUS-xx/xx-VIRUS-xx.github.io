How Claude Code helped me decide: one pass or two?

A design question settled by experiment instead of opinion, and what different models each contributed to the answer.

Prabhat Saxena · 22 October 2026 · 7 min read

I was building an agent that reads receipts and has to say when it might be wrong. One design question kept coming back: is a second reading worth 2.3 times the cost, and should the second reader be the same model or a different one? Opinions on this are easy and cheap. I wanted a number. This post is how Claude Code helped me turn the question into an experiment, what the different models contributed, and where its help stopped and my judgment had to take over.

The decision

The agent reads each receipt, checks the arithmetic in plain code, and marks a row OK or REVIEW. A single reading can never earn an OK, because nothing independent checks it. A second reading can. So the real questions were:

  1. Does a second pass add accuracy, or only a trustworthy signal?
  2. If the same model reads twice, does it catch its own mistakes?
  3. Which model should do the reading, given price and speed?

Why opinion was not enough

Each side had a plausible argument. "A second look catches slips" sounds right. "The same model will repeat the same slip" also sounds right. Both can be true for different models, and I had no way to know which applied to mine without measuring it. Claude Code's first contribution was refusing to let me guess: it asked what the measurement would be, and what ground truth I had. I had none, so the plan had to include building it.

Making the experiment cheap enough to run

The first real call through the headless Claude Code CLI cost $0.34 at list price, because each session carried about 38,000 tokens of tool and skill overhead. Claude Code probed the flags one by one, found that turning off MCP servers, slash commands and settings sources cut it to $0.019, a 17x reduction, and kept the session read-only. That one measurement is what made ten configurations over 45 receipts affordable: 451 model calls for $24.77 at list price, in roughly an hour, with no API key.

The rest of the harness exists to keep me honest: labels written before any model ran, a v1 baseline frozen before I touched anything, and a stated warning that the later v2 numbers are optimistic because the fixes were chosen after seeing the same 45 receipts.

How the different models helped

One receipt prints its date as 13/03/2018. Haiku 5.5 read the year as 2016, on both passes. The two passes agreed with each other, nothing flagged, and the row went out as OK at 0.97 confidence. When Sonnet did the second reading instead, it read 2018, the passes disagreed on the date, and the row dropped to REVIEW at 0.55. I opened the image to confirm: Sonnet was right.

  • A different second reader catches what the same model repeats. Agreement between two readings of the same model is weak evidence, because the same blind spot produces the same wrong answer twice.
  • A weaker model as the checker costs review time. With Sonnet first and Haiku second, 3 rows were flagged instead of 1: Haiku's own misread of that same year, and a day digit (26 or 28) that really is ambiguous.
  • A stronger model removed the need. Sonnet and Opus both got every row right with zero silent errors, so there was nothing for the second pass to catch. Opus cost the same, ran 3.6 seconds slower and flagged one more row.
  • A weaker model shows what the pass is for. Haiku 4.5 checking itself let four wrong rows through as OK.

So I shipped Sonnet for both passes: the cheapest two-pass setup with the best measured result. For a strong model the second pass bought no accuracy. It bought the right to say OK. And I recommend a different model for the second pass whenever the primary is not clearly stronger than the data.

The split matters. Claude Code was strong at generating the alternatives, making the test cheap and finding holes. It had no stake in the answer, which helps, but it also reads the same family of labels as the systems it scored, so the labelling and the sign-off stayed mine.

Where this is thin

The same-model finding rests on one receipt for the strong-ish model, plus four errors from a much weaker one. The labels were drafted by a Claude model and only sample-checked by me. All 45 receipts are Malaysian. The shipped configuration never made an error, so its ability to catch one is unmeasured; zero errors in 45 still allows a true error rate of about 6.4%.

An independent audit of the repository re-derived every headline number from the per-row data and found no mismatch. It also found that one security claim in my docs was overstated; the audit report lists it with a fix.

A way to use this for your own decisions

  1. Write the decision as a question a number can answer. Not "is two passes better" but "how many wrong rows reach a human as OK".
  2. Make the experiment cheap first. Measure the cost of a trial before running many. A 17x saving changes what you can afford to learn.
  3. Let it attack your plan before you build. Five gaps in a flowchart cost nothing; five gaps in code cost a day.
  4. Freeze a baseline. Fixes chosen after seeing results make the results look better than they are. Say so.
  5. Use a second reader that does not share the first one's context. That is the whole lesson of the receipt above, applied to the review itself.
  6. Write down what you did not prove. It is the part a reader trusts most.

The code, the evaluation and the audit report are in the receipt-extraction-agent repository.
